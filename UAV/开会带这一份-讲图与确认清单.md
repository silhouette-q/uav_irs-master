## 第 3 拍 · 右半：排队是补上的关键缺陷（2 分钟）★ 重点

【指】右上四个步骤框

【说】

> "一个时隙内的动作顺序：**先做保留决策**（可卸也可预取，**两者都占 GPU**），
> 然后任务到达、**用户路由**、服务（重载 → prefill → decode）。
> **顺序本身是建模内容** —— 保留动作排在到达之前，所以预取会挡住随后来的请求。"

【指】两条时间轴（上轴 user / 下轴 server）与 epoch 边界虚线

> "**这里是双时标。** 上面这条是用户，**每个时隙**都要决策 —— 任务一到就得选一台。
> 下面这条是服务器，**每 Δ=10 个时隙、也就是 1 秒**才做一次卸载决策。
>
> 为什么是这个方向：路由由到达触发，必须逐任务响应；层保留是 rent-or-buy，
> **它的物理尺度是空闲期**，量级是秒，比 100 ms 的时隙长一到两个数量级。
> 让服务器每 100 ms 改一次主意只会把 PCIe 抖坏。
>
> **epoch 之内服务器不动**，但状态还是会自己往上跳 —— 因为任务被服务后模型必须全常驻。
> 所以'保留状态会自己变高、但只在边界才会主动变低'。"

【指】右中的 task A 长条和 busy-until 虚线

> "这是**跨时隙排队**。任务 A 从 t 占到 **t+2**，B 在 t+1 到达就得等。
>
> **这是我这一版补的最关键的东西。** 之前假设任务瞬时并行完成，
> 会**严重低估时延**，还允许物理上不可能的调度。"

> "补上之后有个副产品：**负载均衡从'公平偏好'变成了'稳定性必要条件'**。
> 总选最近，利用率飙到 **2.36**，队列直接发散。
>
> 还有个反直觉的：**激进卸载会让三台服务器全部越过 1**（1.12~1.56，20 个种子）——
> 说明**卸载省下的显存是拿 GPU 时间换的，不是免费的**。这个在建排队之前完全看不见。"

【落】**"排队不是补充细节，它改变了问题的性质。"**

## B.0 已定（不用他表态，但要主动说）：共享显存维持 C̄ = 24 GB

```
三模型全常驻 = 14728 + 3140 + 270 = 18138 MB
显存容量                          = 24000 MB      ← 富余 5862 MB (24%)
绑定窗口     = 16298 MB ≤ C_bar < 18138 MB
```

⇒ 三个模型可以**同时全常驻**，`can_serve` 恒 True，从不驱逐，显存利用率恒为 0.756。

**决定：维持现状（2026-08-22 自定）**，理由三条：

1. **建模层面约束是完整的**，不是漏了 —— 代码的 `infeasible` 测试用 8 GB 能正确报
   "7B 无法服务"，`memcap` 测试保证 200 组随机状态 clip 后恒满足约束。
2. **主结果跑在"显存不是瓶颈"的配置上是有意的** —— 否则时延与公平的结论会被
   显存挤压污染，分不清哪个效应来自哪里。
3. **把 C̄ 列成第五章的一条敏感性轴**（扫 16.3~18.1 GB 的绑定窗口），
   专门看约束生效时策略怎么变。这样"K 个模型共享一块显存"是一条**受控的实验轴**，
   不是一条永远为真的死条款。

**被问到"那这个约束不是白写了"就答**：它决定了 `can_serve` 与 `make_room_for` 的语义，
也决定了 $\check i$ 的可行性前提（式(6)(7)）；只是主算例落在它宽松的一侧，
敏感性实验会把它推到绑定侧。

> ⚠ 遗留的小矛盾（不影响这个决定，但要知道）：云的显存带宽设成 2000 MB/ms = 2.0 TB/s
> 是 A100-80GB 量级，而显存只给 24 GB —— 市面上没有这种卡。若哪天要修，
> 最省事的是把云改成 80 GB（顺带就让"边缘受显存约束、云不受"成为又一个选云的理由）。

## Q1 ★★★ 长时标 Δ 取多大？

现在默认 **Δ = 10 时隙 = 1 s**（时隙 100 ms）。定它的依据是"层保留是 rent-or-buy，
物理尺度是空闲期 O(1/λ) ≈ 秒"。实测敏感性（400 时隙，同一个种子）：

| Δ (时隙) | = ms | 「立刻全卸」策略的 J | 显存 | 累计加载 (ms) | 「全保留」策略的 J |
|---|---|---|---|---|---|
| 1 | 100 | 11943 | 0.297 | 119564 | 305 |
| 10 | 1000 | 10956 | 0.350 | 111687 | 305 |
| 50 | 5000 | 7650 | 0.544 | 84004 | 305 |

**两个观察**：

1. **Δ 只在策略真的择时卸载时起作用** —— 全保留策略对 Δ **完全不敏感**（一列 305 到底），
   因为它从不主动卸载，状态到了 N 就不再变。
2. ⚠ **别把"Δ 越大 J 越小"当结论**：这里的 unload 策略是"无脑立刻全卸"，本身就是坏策略，
   放慢它只是让它少犯错。Δ 的真实影响要等**学出来的**策略才能判断。

**想请您定**：(a) 1 s 合适吗？(b) 还是应该按 1/λ 来定（最小模型 λ=3 次/秒 ⇒ Δ≈3 时隙）？
(c) 或者干脆把 Δ 也当成要扫的实验参数？

## Q2 ★★★ 奖励这么分账，认不认？

```
用户    r = −ω1·Σ(等待 + 传输 + 计算)/deadline  + ω3·Jain  − 罚项
服务器  r = −ω1·Σ(加载)/deadline               − ω2·显存占用/(M·C̄)
------------------------------------------------------------------
相加 = −J（目标函数取负），Δ∈{1,10} × 3 策略都断言过，误差 <1e-6
```

**依据**：加载是层保留**唯一**控制的时延分量，显存是它的直接后果 ⇒ 归服务器；
等待/传输/计算完全由"选了哪台"决定，Jain 是路由的直接后果 ⇒ 归用户。

**两个我主动交代的点**：

1. **罚项全给了用户**（超 deadline、无可服务节点）。理由：`i_check` 已经保证
   "钉住的模型重载放得进 deadline 预算"，剩下的超时主要来自排队 ⇒ 路由的后果。
2. **预取有外部性**：预取占 GPU ⇒ 抬高后续任务的**等待**，而等待记在用户账上。
   服务器仍间接付费（它省下的重载出现在自己那项里），但一部分机会成本被外部化了。
   代码留了开关 `charge_prefetch_wait_to_server` 可以精确划给服务器 ——
   **那是恒等式内部的重分配，总和不变**。

**想请您定**：这个切法可以吗？还是两边干脆共享同一个全局奖励（好证但 credit assignment 差）？

## Q4 ★★ 是否扩展到多用户？

**现在是单用户**（7-31 组会确认）。它现在的影响变了 —— 因为用户已经是智能体了：

| | 单用户（现状） | 多用户 |
|---|---|---|
| 用户侧 | **1 个 agent**，单智能体 DRL | 多个用户 agent ⇒ 用户之间也要博弈 |
| 服务器间竞争 | **弱**（每时隙最多 K=3 个任务） | **真实的资源争抢** |
| 问题性质 | 一个用户 vs M 个服务器 | 真正的多方博弈 |

**多用户会让"多智能体"这件事在两侧都自己站得住**，代价是模型复杂度和实验量都上升。

## Q5 ★★★ 实验要跟谁比？

| 他可能问 | 怎么答 |
|---|---|
| "compute 6 什么单位？" | GFLOP/ms，即 6 TFLOPS；mem-bw 是 MB/ms，900 = 0.9 TB/s |
| "deadline 在哪？" | 图上没画。它是**唯一的外生 QoS 参数**，橙色的钉住层数就是它的后果。5500 / 900 / 120 ms |
| "为什么显存带宽要单列？" | decode 逐 token 生成，每步要把全部权重读一遍，**受带宽不受算力**限制。实测三台都是带宽受限 |
| "为什么三台不各画一条显存条？" | 三台完全一样（都 76%），画三遍是重复，所以只声明一次 |
| "云的带宽 2 TB/s 配 24 GB 显存？" | **您说得对，这是不一致的** —— 2 TB/s 对应 A100-80GB。这在 **B.0** 末尾记着，选"云改 80 GB"正好一起修 |
| "预取会不会被滥用？" | 不会。预取**占 GPU 并推进忙至时刻**，机会成本内生，不需要额外惩罚项 |
| "Δ 那么大，服务器不就瞎了？" | 不瞎 —— epoch 内它照样在**观测**，只是不改动作；而且状态会因"被服务→全常驻"自己往上跳。真正被 Δ 限制的是"主动往下卸"的时机 |
| "为什么用户观测里要放 epoch 相位？" | 用户得知道"服务器的状态还有多久会变" —— 否则它在 epoch 末尾做的路由判断会基于一个马上要失效的显存快照 |
| "两组 agent 频率不同，怎么训？" | 服务器奖励在 epoch 内累积、边界一次性发放（半 MDP / option 的做法）；恒等式因此对任意 Δ 都成立 |

### 7-31 组会定的场景（更早，也不用再问）
