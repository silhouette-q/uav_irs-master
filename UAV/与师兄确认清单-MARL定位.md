## Q1 ★★★ 多智能体具体用在哪？三种候选结构

我目前实现的是 **A**，但 B / D 都说得通，想请您定。

| | 结构 | 谁是 agent | 动作维度 | MARL 是否必需 |
|---|---|---|---|---|
| **A**<br>（现状） | 服务器兼管卸载 + 竞价接任务 | M 个服务器 | 每 agent **2K**<br>（K 保留 + K 出价） | 是（同时决策、结果耦合） |
| **B** | 中央调度器负责路由，服务器只管卸载 | M 个服务器 | 每 agent **K** | 弱（可退化为单智能体的因子化动作） |
| **D** | 调度器 + 服务器，**异质智能体** | 1 个调度器<br>+ M 个服务器 | 调度器 M 维<br>服务器各 K 维 | 是（不同动作空间、共享奖励） |

**答案会改变什么**：

- 选 **B** ⇒ agent 动作空间**直接减半**，"多智能体"这个卖点弱一半，论文会更像**纯在线缓存**问题
- 选 **D** ⇒ 结构最自然（路由本就是"一个任务去一台"，保留本就是"每台各自的事"），但要处理异质 agent
- 选 **A** ⇒ 保持现状，但需要 Q2 把竞价机制定下来

## Q2 ★★★ "服务器接任务"具体是什么机制？

组会说服务器兼管"接任务"，那就**必须有冲突消解规则**（两台都想接怎么办）。我自行采用了**最高出价者得**：

$$m^\star=\arg\max_{m\,\in\,\text{可服务}} v_{m,k}(t)\ \Longrightarrow\ x_{j,m^\star}=1$$

| 备选 | 说明 |
|---|---|
| **竞价，最高者得**（现状） | 出价 $v_{m,k}$ 是学出来的动作；完全分布式 |
| 中央仲裁 | 调度器收集各服务器状态后决定（= Q1 的 B / D） |
| 接受概率 | 各服务器输出"愿不愿接"的概率，冲突时随机/按序 |

**这条不只是实现细节 —— 它决定论文定位。** 竞价是我发明的，如果不合您的意，越早改越好。

## Q3 ★★ M=3 时单智能体完全可行，为什么要用多智能体？

这是审稿人一定会问的。目前我能给的理由：

1. **可扩展性**：单智能体动作维度是 $M\times K$，随服务器数线性膨胀；MARL 每 agent 只 $K$ 维
2. **分布式执行是场景约束**：真实边缘系统没有一个能实时拿到全局状态的中央控制器
3. **天然部分可观测**：每台服务器只看得见自己的队列、显存、链路

**但 M=3 时这三条都不算强**。想请您定一个口径：

- (a) MARL 是为**大 M**铺路，实验里做 M = 3 / 6 / 12 的可扩展性对比？
- (b) 分布式执行**本身就是场景要求**，不需要额外论证？
- (c) 还是说 M=3 就用单智能体，把重点放在"缓存×路由耦合"上？

## Q5 ★★★ 共享显存约束在默认参数下**从来没绑定过** —— 怎么改？

三台显存都是 **24000 MB**（组会确认"容量相同"）。但：

```
三模型全常驻 = 14728 + 3140 + 270 = 18138 MB
显存容量                          = 24000 MB      ← 富余 5862 MB (24%)
```

⇒ 三个模型可以**同时全常驻**，`can_serve` 恒 True，从不驱逐，显存利用率恒为 0.756。
⇒ **"K 个模型共享一块显存"这个相对论文最主要的新增耦合，在实验里是惰性的。**

（代码本身正确：`infeasible` 测试用 8 GB 能正确报不可行。问题只在默认参数。）

**可行且绑定的窗口很窄**：

```
16298 MB  ≤  C_bar  <  18138 MB
  ↑ 由"近边缘服务 7B"决定: 7B 全常驻 14728 + 其他两模型压到 i_check 1570
                                        ↑ 三模型全常驻和
```

**顺带一个硬件自相矛盾**：云的显存带宽设成 2000 MB/ms = **2.0 TB/s**（A100-80GB 量级），
但显存只给 24 GB —— **市面上没有这种卡**。懂 GPU 的审稿人会注意到。

**四个选项，想请您定**：

| | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 1 | C̄ → **17000 MB** | 一行改完 | 17 GB 不是真实卡容量 |
| 2 | C̄ → **16384 MB (=16 GiB)** | 真实卡尺寸 | 只比下界高 **86 MB**，太脆 |
| **3** | **加第 4 个模型**，让全常驻和超过 24 GB | 24 GB 真实；边缘托管 4 个模型更真实；动作空间也变大 | 要重跑全部数据与两张图 |
| **4** | **显存异质**：边缘 24 GB / 云 80 GB | 最真实；"边缘受显存约束、云不受"是**又一个选云的理由**，路由更有意思 | **与"容量相同"的结论冲突** |

我倾向 **3 或 4**。选项 2 的 86 MB 余量太危险。

## 附：为什么说这不是"纯调度问题"（备答用）

如果被问到"这就是个调度问题吧"，可以这样答：

| | 传统调度 | 本问题 |
|---|---|---|
| 资源 | **给定**，只决定谁先谁后、去哪台 | **会被决策改变** —— 卸载腾出显存，但下次要花时间搬回来 |
| 决策类型 | 分派 | 分派 **+ rent-or-buy（在线缓存）** |
| 对应文献 | 卸载/调度 | 一半是卸载/调度，**另一半是 online paging / ski-rental** |

**两边文献都不处理联合问题** —— 卸载论文（含基础论文）是单服务器无路由；调度论文没有"资源可被部分驱逐再重载"这个结构。**缝隙就在这里。**

还有一条不可替代的理由：**预取需要预测未来到达**，而 ski-rental 是最坏情况算法，天然做不到 —— 这是"为什么非用学习型方法"的硬理由，不是"因为 DRL 流行"。
