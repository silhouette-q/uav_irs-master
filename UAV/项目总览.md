**论文在解决什么**：边缘服务器显存有限、LLM 请求稀疏突发。空闲时把模型层留在显存则响应快但持续占显存；卸载则省显存但下次请求要重新加载（7B 模型满载加载约 4.8 秒）。论文按**层粒度**决定"哪些层、何时卸载"，在**内存成本**与**加载延迟**间权衡并满足 QoS。方法是 **ski-rental（滑雪租赁）+ 拉格朗日对偶**，**不是** DRL —— 这正是我们要用 DRL 替代/增强的对象。

## 3. 当前场景

```
                 ┌─ 无线 (R1, δ1) ─→ Server 1  近边缘   算力弱   显存 C̄
   用户 ─────────┼─ 无线 (R2, δ2) ─→ Server 2  中边缘   算力中   显存 C̄
  (K 类异构任务)  └─ 无线 (R3, δ3) ─→ Server 3  云       算力强   显存 C̄
```

架构图正式版：**`edge-unload-repro/figures/fig_architecture_v3.pdf`**（v3，按 8-21 组会重画；见第 5.5 节）

### 设定（7-31 组会定场景，★ 为 8-21 组会定的决策归属）

| 维度 | 设定 |
|---|---|
| 用户 | **单用户**，按概率随机产生任务 |
| 任务异构性 | ① 需要**不同的模型**（K 个）② **到达率不同**（λ_k） |
| 模型放置 | 每台服务器存**完整**模型，不拆层；一个任务在一台服务器上跑完 |
| 显存 | 各服务器**容量相同** C̄；但 **K 个模型共享**这块显存（新增耦合） |
| 算力 | 各服务器**不同**（云强、边缘弱） |
| 通信 | 无线接入速率 R_m + 回程时延 δ_m，越远越大 |
| 智能体 | ★**用户 1 个 + 服务器 M 个**（异质）：用户决路由（每时隙）、服务器决层保留（每 Δ 时隙） |
| 目标 | 最小化推理时延 + 内存成本，并用 **Jain 公平指数**做负载均衡 |

### 四重张力（问题的核心；v4 新增排队维度）

1. **近但弱** vs **远但强** —— 近端传输 2.2 ms 但计算 3354 ms；云传输 80 ms 但计算 1274 ms
   ⇒ **重任务云最优、轻任务近端最优**，路由非平凡
2. **该模型是否已常驻** —— 加载延迟（约 2100~4100 ms）与计算同量级
3. **K 个模型抢显存** —— 保留 A 模型就得牺牲 B 模型
4. **⭐ 服务器占用/排队** —— 系统总负载 ≈ 256 ms/100 ms 时隙 ⇒ 至少需 2.56 台（现有 3 台），
   所以**负载均衡是稳定性的必要条件**；且**卸载不再容量免费**（重载与推理抢 GPU）

### 两个耦合决策（★ 8-21 组会定了归属与频率）

| 决策 | 谁决定 | 频率 | 拟用方法 |
|---|---|---|---|
| **任务路由** x_{j,m}：任务分给哪台服务器 | **用户**（自己就是一个智能体） | 每时隙 τ=100 ms | DRL |
| **层保留** s_{m,k}：各服务器各模型何时卸载/预取 | **每台服务器**各自决定 | 每 Δ 时隙（默认 10，即 1 s） | MADRL |

二者双向耦合：路由决定了每个「服务器 × 模型」看到的到达率 λ_{m,k}，而 λ_{m,k} 决定最优卸载时机；反过来，某服务器上模型是否常驻又决定把任务分给它是否划算。

**师兄明确要求的一条**：server 的动作必须写进用户的环境 —— 已落在用户观测里的
`D_{m,k,s}/T^max_k`（按当前保留状态算出的预估重载时延）。没有它，用户分不清
"模型还在显存里"和"已经被卸了"。

**为什么用户快、服务器慢**：路由由到达触发，必须逐任务响应；层保留是 rent-or-buy，
物理尺度是空闲期 O(1/λ_k)，比时隙长一到两个数量级。Δ=1 时精确退化为原来的单时标模型。

### 两个最有力的正确性证据

1. **精确退化到论文**：新的多服务器模型在"单服务器 + 单模型 + 无传输无计算"配置下，
   `i_check=3`、`B=30`、TABLE I 四个成本 **100 / 140 / 185 / 225** 全部精确复现。
2. **环境与目标完全自洽**：MARL 环境的**团队累计奖励 == −目标函数 J**（误差 <1e-6），
   三种参考策略下均成立。

### 建模中发现的论文问题

- **论文正文笔误**：`D_i = Σ_{i'≥i} d_i'` 应为 `Σ_{i'>i}`。只有 `>i` 才能复现 TABLE I 的成本，
  也才与状态定义（状态 s_i 已保留第 i 层）和算法伪代码自洽。
- **自动复现论文 C 节结论**：代码算出 `B = η/β`，对所有模型相同 —— 正是论文"d=kc ⇒ 所有直线
  交于同一点 B=ηk"的结果。

### Demo 揭示的权衡（400 时隙，v4 含排队）

| 参考策略 | 超时 | 平均时延 | 最大利用率 ρ | Jain | 显存 | 目标 J |
|---|---|---|---|---|---|---|
| keep+nearest | 181 | 35222 ms | **2.738 ⚠发散** | 0.345 | 0.756 | 33042 |
| keep+roundrobin | 107 | 2451 ms | 0.861 | 0.767 | 0.756 | 1902 |
| **keep+leastbacklog** | **45** | **647 ms** | 0.769 | **0.905** | 0.756 | **305** |
| unload+roundrobin | 175 | 14354 ms | 1.712 ⚠ | 0.891 | **0.347** | 12886 |
| unload+leastbacklog | 180 | 12447 ms | 1.594 ⚠ | 0.962 | **0.350** | 10956 |

**没有固定策略全面最优** —— 这正是需要学习型联合决策的动机。

## 7. 待师兄确认的建模假设

| # | 假设 | 说明 |
|---|---|---|
| **1** | **Δ 取多大** | 长时标 epoch，现默认 10 时隙 = 1 s。实测：对"全保留"策略**完全无影响**；对"立刻全卸"策略从 Δ=1 到 50 使 J 从 11943 降到 7650（显存 0.297→0.544、加载 119564→84004 ms）。⚠ 那是**坏策略被放慢的假象**，真实影响要等学出来的策略。跑 `demo_multi_server.py` 看第 ⑤ 张表。 |
| **2** | **奖励分账是否认可** | 用户背 等待+传输+计算+公平+罚；服务器背 加载+显存。已知外部性：预取抬高的**等待**记在用户账上（代码留了 `charge_prefetch_wait_to_server` 开关做重分配，恒等式不破）。 |
| **3** | **"简单规则辅助"用在哪一侧** | 师兄提到可引入简单规则。若用在服务器侧，`i_check`/`B` 的解析约束正好是现成的规则。 |
| ~~4~~ | ~~共享显存要不要人为收紧~~ → **已自行决定（2026-08-22）：维持 C̄=24000 MB** | 主算例保持"不绑定"是**有意的**（全常驻 18138 < 24000）—— 这样时延/公平的结论不被显存挤压污染。改为把 **C̄ 列成第五章的一条敏感性轴**，扫绑定窗口 16298~18138 MB。约束本身建模完整（`infeasible`/`memcap` 覆盖）。遗留小矛盾：云 2 TB/s 配 24 GB 没这种卡，若要修就把云改 80 GB。 |
| 5 | decode 的带宽模型 | 用 `max(算力, 显存带宽)`；更精细可加 KV-cache 随上下文增长。 |
| 6 | 排队为单服务器 FIFO | 传输与计算流水；若 GPU 支持批处理需改多服务台。 |
| 7 | 权重默认 ω=1 | 三项已归一化故可解释；正式实验建议做敏感性分析。 |

> ✅ **2026-08-21 组会已解决**（原第 1、2 条）：竞价机制 → **驳回，路由归用户**；

> 放置变量 y 是否升为长时标决策 → **保持给定**（长时标让给了层保留）；硬件同构性 → 不影响建模。
> ✅ **已在 v4 修复**（原为待确认项）：计算时延已拆 prefill/decode；已允许预取；
> QoS 双重形式已统一为"deadline 唯一，D^QoS 由其推导"；目标三项已归一化。
